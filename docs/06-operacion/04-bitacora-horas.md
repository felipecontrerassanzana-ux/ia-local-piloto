# Bitácora de horas por proyecto

Distinto de `03-monitor-estado.md`: `/estado` y `/` responden "¿está funcionando el servidor ahora?" — esto responde "¿cuánto tiempo activo se le dedicó a cada proyecto, qué días, a qué hora?", a partir del historial real de sesiones de Claude Code de la cuenta de Windows que lo genera (no de esta app ni de Qwen Code/Goose — ver el porqué más abajo). Se sirve desde el mismo servidor del monitor (`/bitacora`) solo por conveniencia de implementación (reutiliza el `HttpListener` y la regla de firewall que ya existen) — es una funcionalidad separada, no una parte del chequeo de salud del stack.

**Origen:** Felipe pidió medir cuánto tiempo propio invierte en cada proyecto — se prototipó primero como Artifact de Claude (iteración rápida, varias vueltas de diseño) y, una vez validado el concepto, se portó a un script real de este repo para que no dependa de Claude ni de claude.ai para actualizarse — mismo argumento que ya justifica por qué `/estado` tampoco es un Artifact (ver `03-monitor-estado.md`).

## Qué hace, en concreto

- **`scripts/bitacora-horas.ps1`** — lee `~/.claude/projects/**/*.jsonl` de la cuenta de Windows que lo corre, calcula tiempo activo con huecos (un hueco entre dos eventos consecutivos mayor al umbral configurado no cuenta como trabajo — configurable en `bitacora-proyectos.json`), detecta el proyecto de cada tramo mirando qué rutas de archivo tocaron las herramientas invocadas (no el texto de la conversación), y suma también tokens de entrada/salida por proyecto (mostrados aparte, no mezclados con el tiempo — varían según la complejidad de la tarea, no son un buen proxy de esfuerzo). Genera `logs/bitacora-horas.html`. Sin permisos de administrador — solo lee logs propios.
- **`scripts/bitacora-horas.bat`** — corre el script y abre el resultado en el navegador predeterminado (`-AbrirNavegador`); la ventana se cierra sola si todo sale bien, y solo queda abierta si hay un error para poder leerlo.
- **`scripts/bitacora-proyectos.json`** (fuera de git, ver `.gitignore`) — qué proyectos reconocer. Se separó del script a propósito: los nombres de los otros repos de Felipe (`ia-tecnoingenieria`, `cumplimiento-tecnoingenieria`, etc.) no deben quedar hardcodeados en este repo — mismo criterio de independencia que ya se aplica entre `ia-local` y Tecnoingeniería. El repo trae `bitacora-proyectos.example.json` (genérico, versionado) como plantilla.
- El monitor sirve el HTML ya generado en `/bitacora` — **no lo recalcula en cada request** (parsear los `.jsonl` puede tardar segundos y crece con el tiempo); correr el script a mano cuando se quieran números al día.

## Por qué esto mide por cuenta de Windows, y no hay (todavía) una separación real Felipe/Vicente

El equipo del piloto es de uso compartido (ver `../02-modelo/03-hardware-real.md`). Investigado 2026-08-28 antes de construir esto:

- **Qwen Code y Goose, corriendo contra el Ollama local de este piloto, no tienen ningún login ni cuenta asociada** — a propósito, para no depender de ningún servicio externo (confirmado revisando su documentación oficial: no hay variable de entorno ni concepto de "usuario" que capturar). No hay ningún correo ni ID ahí para segmentar por persona.
- **Open WebUI sí tiene multiusuario real** — login local por correo/contraseña, cada cuenta con su propio historial de chat (`chat_message.user_id`, ver `../07-referencia/05-open-webui.md`), confirmado en `docs.openwebui.com`. Si Felipe y Vicente usan Open WebUI (chat/RAG) con cuentas separadas, esa separación **ya existe sola**, sin construir nada — pero solo cubre el uso por chat, no el de los agentes de código (Qwen Code/Goose).
- **Conclusión aplicada acá:** para los agentes de código, la única separación real disponible hoy es la **cuenta de Windows** — cada persona logueada con su propio usuario tiene su propio `~/.claude/`, `~/.qwen/`, etc., sin mezclarse. `bitacora-horas.ps1` ya lee de `$env:USERPROFILE`, así que si Vicente lo corre con su propia cuenta, obtiene su propia bitácora sin cambiar una línea de código — **pendiente de decidir** si van a usar cuentas de Windows separadas en el equipo compartido (no resuelto todavía, ver `docs/decisiones.md`).

## Estado de repo (local vs. GitHub) por proyecto

Felipe preguntó si valía la pena saber, para cada proyecto de la bitácora, si vive solo en el equipo o está respaldado en GitHub — relevante porque horas invertidas en un proyecto que nunca se subió a ningún lado es tiempo sin respaldo real. Si un proyecto en `bitacora-proyectos.json` trae `repoPath`, el script corre `git` sobre esa carpeta (una vez por proyecto al generar, no por cada bloque de tiempo) y muestra un badge en la tarjeta de descripción: **"GitHub · al día"** (verde), **"GitHub · cambios sin commitear"** / **"N commits sin pushear"** (ámbar), o **"solo local, sin remoto"** (ámbar) — proyectos sin `repoPath` configurado (ej. DeepTutor, que es un contenedor Docker sin repo git; el mapa `PROYECTOS.md`, que vive fuera de cualquier repo a propósito) simplemente no muestran badge, no es un error.
